# SWERV AI Demand Forecasting Prototype

This separate Python workspace creates a synthetic hourly dispatch-demand
dataset. Every row is generated by code and labeled `data_source=synthetic`.
The data does not represent actual SWERV demand and must not be used to claim
real-world forecast accuracy.

## Setup and generation

From the project root:

```powershell
cd ml/demand_forecasting
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m src.synthetic_dataset
```

The generator saves `data/synthetic_hourly_demand.csv`. It covers every UTC
hour from 2024-01-01 00:00 through 2025-12-31 23:00, including the leap day in
2024. A fixed random seed makes the generated dataset reproducible.

The target column is `request_count`: the number of synthetic requests created
inside that UTC hour. Zero-demand hours remain in the dataset. Generated demand
includes hourly and weekday/weekend patterns, a gradual two-year trend, mild
monthly variation, random count fluctuations, and occasional spikes.

Each row also contains the UTC timestamp, hour, weekday, weekend flag, month,
and a normalized trend index.

## Train and evaluate

After reviewing the generated CSV, train the three comparison models:

```powershell
python -m src.training
```

The pipeline creates hour, weekday, month, and weekend features from each UTC
timestamp. It also creates previous-hour, previous-day same-hour, previous-week
same-hour, and trailing 24-hour average features. Each lag is shifted so it
contains only counts observed before its prediction timestamp. The first week
is omitted because those rows do not have every required lag.

Rows are split by time: the earliest 70% for training, the next 15% for
validation, and the latest 15% for final testing. Linear Regression, Random
Forest, and Gradient Boosting are compared by validation MAE. The final test is
used only once for reporting the selected model; the selected model is refit on
training plus validation rows before that test.

Generated outputs are saved inside this workspace:

- Model: `models/synthetic/best_demand_model.joblib`
- Feature allowlist: `models/synthetic/feature_columns.json`
- Model version and provenance: `models/synthetic/best_demand_model.metadata.json`
- Training and validation metrics: `data/processed/training_validation_report.json`
- Final test metrics: `data/processed/final_test_report.json`

All data and metrics are synthetic. They do not establish real-world SWERV
forecasting accuracy.

## FastAPI forecast service

The API is separate from the delivery-time and agent-assignment services. It
loads the saved artifact from this workspace and does not connect to MongoDB.
Start it on port 8004 from `ml/demand_forecasting`:

```powershell
python -m uvicorn src.api:app --host 127.0.0.1 --port 8004
```

`GET http://127.0.0.1:8004/health` reports model availability, model version,
and that its training source is synthetic.

`POST http://127.0.0.1:8004/predict` requires a UTC hour-aligned start, 1 to
168 forecast periods, and exactly 168 non-negative observed counts for the
hours immediately before that start. Requiring recent history makes the
forecast inputs explicit; the service does not read a database or silently use
the older synthetic CSV as current history.

Example request, using a Python list to show the required 168 hourly values:

```python
{
    "forecast_start_timestamp": "2026-01-01T00:00:00Z",
    "forecast_periods": 3,
    "historical_request_counts": [2] * 168,
}
```

Example response:

```json
{
  "forecast_start_timestamp": "2026-01-01T00:00:00Z",
  "forecast_periods": 3,
  "predictions": [
    {"timestamp": "2026-11-08T00:00:00Z", "request_count": 0},
    {"timestamp": "2026-11-08T01:00:00Z", "request_count": 0},
    {"timestamp": "2026-11-08T02:00:00Z", "request_count": 0}
  ],
  "model_version": "gradient_boosting-synthetic-a62c1700d5fb",
  "training_source": "synthetic",
  "synthetic_provenance": "Trained on generated synthetic hourly demand data; real-world SWERV accuracy is not validated."
}
```

For periods after the first forecast hour, the service uses earlier predicted
counts for lag features. It never has or reads future actual counts. Invalid
timestamps, insufficient history, invalid horizons, and unavailable models
return clear HTTP 422 or 503 errors.

## Real-data status and future modeling

The current MongoDB assessment found only 18 real requests across two UTC
dates. That history is not enough to estimate dependable hourly patterns. Keep
this synthetic CSV separate from real dispatch records and identify its source
in any report or chart.

When there is enough real history, demand should be counted by request
`createdAt`, not by current status or delivery completion time. Candidate
features include hour, weekday, month, past hourly or daily request counts,
and a coarse pickup zone where coverage is sufficient. Lag and rolling features
must use only earlier buckets.

Linear Regression can serve as a baseline, with Random Forest and Gradient
Boosting as comparisons. Use chronological training, validation, and final
test periods; do not randomly split time-series rows. Any fitted preprocessing
must use training data only. Synthetic evaluation remains separate from
real-world validation.
